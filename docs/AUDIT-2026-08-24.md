## P0 — rider-visible breakage

### P0-1 · Clean applies the arterial penalty TWICE (still over-routes)
`road-tier.js` + `RoadTier.swift`. The arterial fix lowered `CLEAN_TIER_COST.arterial`
5.5 → 1.4. But `e4FlagsForProfile(cleanest, …)` returns **`preferBackRoads: true` always**
(road-tier.js:204 / RoadTier e4Flags), and `e4PreferBackRoadsMult(arterial, true)` =
**4.5** (road-tier.js:173). In find-path-v2.js:128-137 the Clean step cost is
`cleanLeafCostMult(tier,family) × e4LeafCostMult(...)`, so **effective arterial =
1.4 × familyCost × 4.5 = 6.3×/km** (was 5.5 × 4.5 = 24.75× before the fix).
- **Why it matters:** the tier cost ALREADY encodes the back-road preference (collector
  0.86, local 0.92 < arterial 1.4). The always-on E4 `preferBackRoads ×4.5` is a
  *redundant second* arterial penalty that likely keeps the metro loop alive (arterials
  still ~6× a back road). The 5.5→1.4 change reduced it 4× but did not remove the double
  count.
- **Fix:** for Clean, don't double-count. Either (a) `e4FlagsForProfile(cleanest)` →
  `preferBackRoads: false` and let the tier cost express the preference (arterial = 1.4×),
  or (b) keep prefer-back always-on but set `CLEAN_TIER_COST.arterial = 1.0`. Test
  Halifax→(44.9033,-63.2449) Clean km after — expect it to actually collapse to sane.
- **Lockstep note:** the bug is present in BOTH engines (Swift `RoadTier.e4Flags` also
  returns `preferBackRoads: true` for cleanest), so it's consistent (offline == online) —
  but the fix must land in both `road-tier.js` AND `RoadTier.swift`.

### P0-2 · Allow Unknown *looks* dead — but it's a SYMPTOM of P0-4, not a wiring bug
CORRECTION to my earlier read: the wiring is present and correct.
`accessAllowed` (find-path-v2.js:198-210) makes `motorized_unknown` edges eligible only
when `policy.motorizedUnknown` is true (and never for cleanest); `normalizePolicy`
(router.js:703-717) sets `motorizedUnknown = isClean ? false : requested` from the flag;
and dirt/direct get a 0.5× discount on unknown edges when on (find-path-v2.js:1112-1116).
The toggle produced identical routes because **B1 removed the `highway=path` edges, and
path defaults to `motorized_unknown` access** — so at Myra/Porters Lake there are no purple
edges left for Allow Unknown to open. It's dead *because the trails are gone*, not because
the switch is unwired.
- **Fix:** none needed on the switch itself; restoring paths (P0-4) revives it. VERIFY:
  after restoring paths, toggle Allow Unknown on a route near track/path and confirm the
  route changes.

### P0-3 · Dirt / Balanced / Direct route on COARSE surface, not the v3 leaves
`profile-costs.js` tables use the old 5-bucket coarse codes (paved/gravel/access/track/
unknown). Only Clean (`road-tier.js`) was migrated to leaf families. So the un-compressed
detail (fine_gravel vs sand vs mud, road-class tiers) feeds Clean + stats/% ONLY — the
three profiles the rider actually uses can't tell easy gravel from technical sand.
- **Why it matters:** this is the core value of the whole v3 effort, only half-connected.
- **Fix (bigger, later):** add leaf surface-family cost tables for direct/balanced/dirt,
  used when `hasLeaves`, coarse fallback otherwise. One profile at a time.

### P0-4 · Trails: code is FIXED, but the LIVE PACK is stale (real root = pack/code skew)
UPDATE after reading osm-roads.js: `path` is **already restored** (INCLUDE_HIGHWAY:68 keeps
all track + path; cycleway dropped; atv overrides vehicle-type deny but not hard land deny —
that logic is correct). So the trail-removal *code* is fixed. The rider still sees no trails
because **the deployed pack is stale** — see P0-5.

### P0-5 · PACK/CODE VERSION SKEW — the live pack is behind the code (this explains a LOT)
Rick's 2026-08-24 route-identity shows `graph=555034df… = ns-v3-20260823-03` (the **G1
ferry-era pack**) while the engine is `build=92a8112` (post-sprawl, much newer). The G2
return claimed it published `8a17f47… (ns-v3-20260823-04)`, but the live pack is the OLDER
`03`. So the pack went **backward** relative to the code.
- **Consequence:** every PACK-dependent change is NOT live even though the CODE is:
  - `path` restore (P0-4) — not in pack `03` → trails still gone.
  - G2 structure (fords/tunnels/overpasses) — not in pack `03`.
  - possibly the honest-surface leaf refresh.
  Rick has been testing *code* fixes (live via the Vercel engine) against a **stale pack**.
  Half of what looked broken is "the fix isn't in the pack he's routing on."
- **ROOT CAUSE (found it):** `publish-packs-cdn.js` `syncR2()` (lines 139-145) returns
  `false` and prints "R2/S3 sync skipped" when `AWS_ENDPOINT_URL` / `R2_BUCKET` /
  `AWS_ACCESS_KEY_ID` are absent — and `main()` **ignores that return value, so the script
  still exits 0 (success)**. Every pack "publish" that ran without R2 creds reported success
  while uploading NOTHING. The Vercel engine deploys via git (works); the pack R2 sync
  silently no-ops → code advances, live pack frozen at `03`. Cursor's "published/deployed"
  reports were true for the code, false for the pack, and nothing failed loudly.
- **This is THE reason pack-dependent fixes never reached the device.** Not a routing bug —
  a silent-success deploy bug.
- **Fix (do FIRST in the morning):**
  1. Make `syncR2()` **fail loud**: if not `--local-only` and creds are missing (or the
     `aws s3 sync` didn't run), `process.exit(1)` — a publish that can't reach R2 must be a
     hard error, never a silent success. Have `main()` check the return value.
  2. Set the R2 creds (`AWS_ENDPOINT_URL`/`R2_BUCKET`/`AWS_ACCESS_KEY_ID`) in the env that
     runs the publish.
  3. Rebuild NS from HEAD, publish for real, then **curl the live endpoint and assert the
     served `graph=` hash == the freshly built hash** (the DoD check, actually enforced).
  Only THEN re-test — several P0s (trails, structure) may partly resolve once the pack is
  actually current.

## P1 — wrong / risky, will bite

### P1-1 · THE reason we missed everything: tests assert cost-function outputs, never route sanity
This is the systemic hole behind "how did we miss the wrong rules."
- `road-tier.test.js:67-72` asserts `cleanLeafCostMult(ARTERIAL,"paved") === 1.4` and
  `collector < arterial < motorway`. It tests the tier cost **in isolation** — never the
  compounded `tier × e4PreferBackRoads(4.5)` that Clean actually routes with. So the unit
  test is GREEN while the effective arterial cost (6.3×) loops the route. False confidence.
- `metro-balanced-regression.test.js:120-121` asserts only `distanceMeters > 0` — a 162 km
  loop passes.
- `router.dirt-objective.test.js:27,37` assert `dirtPercent >= 70` / `45–55` — dirt-seeking
  works, but nothing caps distance, so a sprawl passes.
- **There is no test anywhere that asserts route DISTANCE vs crow-flies** (e.g. "Halifax→X
  Clean ≤ 1.6× crow", "no route wanders > N km cross-track"). Every over-routing bug
  (Clean loop, Dirt sprawl) slipped through because the suite checks that the *pieces*
  return the right numbers and that dirt% hits a target — never that the *emergent route*
  is sane.
- **Fix:** add end-to-end route-sanity regression tests on fixed NS pin pairs per profile:
  assert distance ≤ K×crow, cross-track ≤ M, and profile-appropriate dirt%. These are the
  tests that would have caught all of tonight's bugs. Make them part of the gate.

### P1-2 · Fuel refuels at 94% of range (the "stretches to the wall")
`fuel-chain.js:409` `targetUse = preferredMax * 0.94`; overflow (`>preferredMax`) ranked
after but progress score still favors the farthest in-window pump. Confirms the diagnosis.
- **Fix (already prompted):** comfort-window — prefer stations in [0.50, 0.80]×cap; >80%
  desperation-only. Change `targetUse` to ~0.65×cap and gather candidates across the range,
  not just the furthest K.

### P1-3 · Dirt allows lateral detour to collect dirt (picker resists backtrack, not sideways)
`chooseDirtRideCandidate` (find-path-v2.js:485-511) is better than the earlier diagnosis:
it filters "coherent" candidates (backward ≤ max(5km, 8%)) and only keeps a looping wider
candidate for a ≥10-point dirt gain. So *backtracking* is well-controlled. But lateral
detour is only weighted `+ lateralMeters × 0.25` (line 505-507), and the Dirt cost table
rewards unpaved ~950× (track 0.0168 vs paved 16). So Dirt still fans *sideways* within the
60 km corridor to collect dirt (79 km for a 17 km crow trip, 25 km cross-track). Reads as
broken to the rider.
- **Fix (tuning, Rick's call):** raise the lateral weight in the picker (0.25 → higher)
  and/or a Direct-style path-length cap for Dirt. One lever, tested with a distance
  regression (P1-1).

### P1-5 · Clean search is UNBOUNDED — no safety net behind the cost table (+ doc mismatch)
find-path-v2.js:522-531 gives cleanest `widthMultipliers = [Infinity]` ("no corridor ladder
— one fabric search"), but router.js:277 documents cleanest as a **"tight Google-style
pavement corridor."** Intent says bounded, code says unbounded. With no geometric corridor,
the ONLY thing stopping Clean from wandering the whole province is the cost table — so the
arterial miscalibration (P0-1) produced a 162 km loop with nothing to cap it. Fixing P0-1
removes the *incentive*, but Clean still has no *bound*.
- **Fix (belt-and-suspenders):** give Clean a corridor or a path-length cap (like Direct's
  15 km budget) so a cost bug can never again produce a province-wide loop. Reconcile the
  code with the documented "tight corridor" intent.

### P1-4 · Structure `parseOsmDuration` boundary is ad hoc
`ferry.js:44-49`: bare numbers `<180` → minutes, `≥180` → seconds. A ferry tagged
`duration=180` (meant as 3 h) parses as 180 **seconds**. Low impact in NS (short ferries),
but wrong at the boundary. **Fix:** require explicit HH:MM or a unit; don't guess at 180.
